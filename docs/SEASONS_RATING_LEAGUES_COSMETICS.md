## 1. Сезоны

### 1.1. Таблица `public.seasons`

| Колонка | Смысл |
|---|---|
| `id` | **Номер сезона.** Он же PK, он же «Сезон №N» в интерфейсе. Отдельной колонки номера нет: PK уже даёт обязательность и уникальность, а весь код (`season_results.season_id`, `season_bundles.season_id`, `order by id desc limit 1`) считает `id` хронологией. |
| `title` | Название сезона. `null` у сезонов, созданных до миграции 051. |
| `status` | `planned` \| `active` \| `completed`. Единственный однозначный признак состояния. |
| `starts_at` / `ends_at` | Плановое окно, `timestamptz`. `null` у исторических сезонов — оно не выдумывается. |
| `start_date` / `end_date` | Календарные даты по МСК. Остались от модели до 051 и продолжают использоваться экономикой (`close_season`, окно штрафов, плашка «уйдёт с витрины через N дней»). |

**Инвариант совместимости** (`check ((status = 'active') = (end_date is null))`):

> `end_date is null` ⇔ сезон идёт.

У `planned` и `completed` `end_date` заполнен: у запланированного — плановой датой
окончания. Благодаря этому ~10 существующих селекторов вида
`select id from seasons where end_date is null order by id desc limit 1`
(в `close_season`, `award_season_points`, `ensure_league_membership`,
`ensure_season_rotation`, `get_student_league_snapshot`, `preview_league_close`,
клиентских запросах магазина и учительской) **не переписывались** и продолжают
означать «текущий сезон». Новый код пользуется `public.current_season_id()`.

Единственное место, где «`end_date` не null» раньше значило «сезон закрыт» —
`supabase/functions/_shared/db.ts::fetchLatestClosedSeasonId` (лиговые уведомления
`main.py`); там теперь фильтр `status = 'completed'`.

Ровно один активный сезон обеспечивает частичный уникальный индекс
`idx_seasons_one_active on seasons((true)) where end_date is null`.

### 1.2. Планирование (сайт учителя)

Раздел **Планирование → 🗓️ Сезоны** (`teacher.html`, `js/teacher-students.js`).
Форма: номер, название, начало, окончание. Время вводится и показывается в **МСК**
(`Europe/Moscow`, UTC+3 круглый год); на сервер уходит ISO со смещением `+03:00` —
часовой пояс устройства учителя и UTC не смешиваются.

RPC (все `SECURITY DEFINER`, внутри проверяют `app_role = 'teacher'` из JWT):

| RPC | Что делает |
|---|---|
| `admin_list_seasons_self()` | Список всех сезонов: статус, номер, название, окно, число фактических участников лиг, число архивных итогов, флаг «срок вышел». |
| `admin_create_season_self(number, title, starts_at, ends_at)` | Планирует сезон. |
| `admin_update_season_self(...)` | Меняет **только** `planned`. |
| `admin_delete_season_self(id)` | Снимает **только** `planned` и только пока к нему ничего не привязано. |

Валидация (коды ошибок → русский текст в `SEASON_ERROR_TEXT` на клиенте):
`season_number_required`, `season_number_taken`, `season_number_too_small`
(номер обязан быть больше последнего — иначе ломается `order by id` как хронология),
`title_required`, `window_required`, `window_order`, `start_in_past`, `season_overlap`
(окна сезонов не пересекаются: сезоны строго последовательны, одновременно активен один).

**Безопасность.** Прямая запись в `seasons` отозвана у `anon`/`authenticated`
(миграция 043), политика чтения — `using (true)`. Ученик, вызвав административную RPC
напрямую, получает `forbidden`: роль проверяется на сервере, скрытая кнопка правами не
является.

### 1.3. Механизм активации — ленивый, на обращении

**Cron в инфраструктуре проекта нет** (нет `pg_cron`; фоновые задачи `main.py` — это
рассылки через `student-bot-api`, а не планировщик БД). Поэтому переход состояний
сделан тем же паттерном, которым в проекте уже создаётся сезон — лениво, на обращении:

```
Mini App / учительская
        └─ ensure_current_season()          (definer, student|teacher)
               └─ ensure_season_schedule()  (advisory-lock на транзакцию)
                      ├─ finish_season(active)      если ends_at <= now()
                      │                             или подошёл плановый преемник
                      └─ start_next_season()        активирует plan, иначе создаёт ad-hoc
```

Вызывается при загрузке профиля (`loadProfile`) и при открытии вкладки «Лидеры»
(`loadLeaderboard`) — то есть на любом открытии приложения.

- До `starts_at` сезон имеет статус `planned` и текущим не становится.
- При наступлении `starts_at` он становится `active` (`start_date` остаётся **плановой**
  датой начала, даже если активация случилась позже).
- После `ends_at` активный сезон завершается, и сразу активируется следующий: подошедший
  по плану, иначе ad-hoc «сегодня». Активный сезон существует всегда — на этом держится
  весь остальной код.
- Ручное закрытие учителем (`close_season` → `close_season_self`) пользуется теми же
  примитивами; только у него остаётся защита «сезон, открытый сегодня, закрыть нельзя».

### 1.4. Идемпотентность завершения

`finish_season(p_season_id)`:

1. блокирует строку сезона `for update`;
2. если `status <> 'active'` — выходит, вернув `already_completed: true` (ни архива, ни призов);
3. **первым действием** переводит сезон в `completed` — конкурент, ждавший блокировки,
   увидит уже завершённый сезон;
4. архивирует итоги в `season_results` (`on conflict (season_id, student_id) do nothing`);
5. выдаёт призы топ-3 с ненулевыми очками (100/60/30, фонд ≤ 190);
6. активирует следующий сезон, вызывает `close_league_season`, обнуляет `students.rating`.

Всё — одна транзакция. Повторное открытие приложения, retry сети и второй клик учителя
второго завершения не производят.

## 2. Рейтинг

Два разных понятия:

| | Сезонный рейтинг | Общий (пожизненный) рейтинг |
|---|---|---|
| Где | `students.rating` | **не хранится** — вычисляется |
| Формула | накопленные очки текущего сезона | `sum(season_results.points)` по всем завершённым сезонам `+ students.rating` |
| Обнуление | да, при завершении сезона | нет и не может: слагаемые независимы |
| Где показан | экран лиги, место в когорте | «Лидеры» → «Общий топ» |

Функции: `public.student_lifetime_points(student_id)`,
`public.get_global_top_self(limit, offset)`.

**Почему двойное завершение не удваивает итог.** Общий рейтинг нигде не хранится и
никогда не инкрементируется — он пересчитывается из архива при каждом чтении.
Даже если бы `finish_season` отработала дважды, `season_results` защищена
`unique(season_id, student_id)` + `on conflict do nothing`, а `status`-гейт не пускает
второй прогон вообще.

**Глобальный топ.** `get_global_top_self` возвращает **всех** зарегистрированных
учеников (в схеме нет ни статуса удаления, ни блокировки — фильтровать нечего, и
выдумывать такие статусы нельзя), с постраничной выдачей и `total_students` в каждой
строке. Сортировка полностью детерминирована:

1. общий рейтинг ↓;
2. очки текущего сезона ↓ (существующий дополнительный критерий);
3. имя ↑;
4. `telegram_id` ↑.

Топ **не** ограничен участниками текущего сезона или текущих лиг. Скрытого «первых 10»
больше нет: клиент листает страницами по 50 до `total_students`.

Имена и косметика чужих учеников приезжают внутри самой RPC
(`student_public_cosmetics`), потому что `students` и `student_equipment` закрыты RLS
«своя строка + учитель» (миграции 042/043) и прямым select не читаются.

## 3. Лиги

### 3.1. План участия и факт участия

`league_memberships.activated_at` разделяет два состояния:

| `activated_at` | Что это |
|---|---|
| `null` | **заготовка посева.** Создана `build_season_cohorts` при старте сезона (snake-seeding по месту прошлого сезона). Невидима: ни в списке лиги, ни в снимке, ни в учительском превью, ни в лиговых уведомлениях бота. |
| не `null` | **фактическое участие.** Ученик реально вступил в битву лиг. |

Заготовки нужны, чтобы сохранить существующую механику лестницы: `close_league_season`
по-прежнему видит **все** memberships сезона, поэтому размеры когорт, счётчик
`inactive_seasons` (два пустых сезона подряд → понижение до Бронзы) и таблица
адаптивных переходов не изменились. `close_league_season` этим этапом не менялась.

### 3.2. Как ученик вступает в лигу

**Только после первого фактического положительного начисления рейтинга в этом сезоне.**
Ни регистрация, ни вход в приложение участия не дают.

Точка входа — `add_season_points()`: единственное место, где `students.rating` растёт.
При `p_amount > 0` она вызывает `ensure_league_membership()` в **той же транзакции**,
поэтому рейтинг не может начислиться без участия. Это покрывает все пути начисления,
включая legacy-приёмку ДЗ (`settle_legacy_approval`), которая ходит в `add_season_points`
напрямую, минуя ledger, и раньше лиги не касалась вовсе.

`ensure_league_membership()`:

- есть заготовка посева → проставляет `activated_at` (`where activated_at is null`);
- заготовки нет (новичок, который ещё ни разу не набирал очков) → кладёт в
  `late_entry`-когорту Бронзы (до 30 человек, при переполнении — следующая) уже
  активированной.

Идемпотентность: участие уникально по `(season_id, student_id)`, активация делается
`where activated_at is null`, вставка — с `on conflict … do update` только по
`activated_at`. Повтор, retry, перезагрузка и второе домашнее задание второго участия не
создают и когорту не меняют.

Отрицательные корректировки участия не создают и **не снимают**: правила выхода из лиги
в проекте нет, снижение рейтинга до нуля оставляет ученика в списке.

**Существующие данные.** Bootstrap миграции 019 залил в `student_league_state` всех
учеников, из-за чего в лигах оказывались пустые аккаунты. Backfill 052:

- закрытые сезоны — все memberships считаются фактическими (история не «пустеет»);
- текущий сезон — активируются те, у кого есть положительная запись в
  `season_points_log` этого сезона (момент вступления берётся оттуда, не выдумывается)
  либо положительный `students.rating` сейчас;
- ученики с положительным рейтингом вообще без участия — добавляются через
  `ensure_league_membership`;
- ученики с нулевым рейтингом не добавляются.

### 3.3. Полный список участников

`get_student_league_standings_self()` отдаёт **всех фактических участников своей лиги**
(tier) текущего сезона: и обычную когорту, и `late_entry`, отдельными группами. Места
считаются **внутри когорты** тем же tie-break, что `close_season`/`preview_league_close`
(очки ↓ → меньше штрафов в сезоне ↑ → раньше набрал очки ↑ → `telegram_id` ↑). Когорты и
сезоны не смешиваются. `LIMIT` отсутствует полностью.

Почему раньше было видно не всех — три независимые причины, все устранены:

1. клиент строил список из `preview_league_close`, где стоит `where m.is_late_entry = false` —
   вступившие по ходу сезона в выдачу не попадали вообще;
2. сам late-entry ученик получал ранний выход без списка;
3. имена и косметика остальных тянулись прямыми select из `students` /
   `student_equipment`, закрытых RLS «своя строка» (миграции 042/043) — ученику
   возвращалась ровно одна строка, его собственная.

## 4. Магазин, владение, инвентарь, экипировка, витрина

Четыре разных понятия, которые раньше путались:

| Понятие | Хранение | Смысл |
|---|---|---|
| **Магазин** | `shop_items.active = true`, для ротации — только бандл текущего сезона (`season_bundles`, `ensure_season_rotation`) | что можно **купить сейчас** |
| **Владение** | `student_items` | что принадлежит ученику. Постоянно, сезоном не ограничено |
| **Инвентарь** | производное представление: `get_student_inventory_self()` | UI-раздел во вкладке «Ещё» — весь список того, чем владеешь |
| **Экипировка** | `student_equipment`, `unique(student_id, slot)` | что надето. В слоте всегда не больше одного предмета |
| **Витрина** | `student_showcase`, 3 позиции, `kind ∈ (item, achievement)` | что показано в профиле |

Экипировка и витрина — **независимые состояния**: предмет может быть надет и не стоять
на витрине и наоборот. Ни одно из действий не перезаписывает другое.

Фактические слоты каталога (`shop_items.slot`): `background`, `frame`, `name_color`,
`crown`, `title`, `status_emoji`. Новые слоты не выдумывались; слот, не попавший в
известный порядок, уходит в раздел «Другое», а не исчезает.

### 4.1. Почему старые предметы не надевались и что исправлено

- **Сервер:** `equip_item` искал слот как `… where item_code = ? and active` — предмет,
  снятый с продажи, надеть было нельзя. `set_showcase` такого гейта не имел и проверял
  только владение — отсюда наблюдаемая асимметрия «на витрину можно, надеть нельзя».
  Исправлено: каталожная строка читается **без** фильтра `active`, проверка владения по
  `student_items` осталась серверной и обязательной.
- **Клиент:** единственная кнопка «Надеть» жила на карточке магазина, а магазин рисует
  только `active = true` и только текущий бандл — карточки предмета прошлого сезона на
  экране просто не было. Исправлено разделом **«Инвентарь»** во вкладке «Ещё».
  Управление старыми предметами в магазин намеренно **не** возвращалось.

### 4.2. Почему старые предметы остаются воспроизводимыми

`item_code` — PK каталога; `render_payload`, `name` и `slot` живут в `shop_items`, а не в
записи о покупке, поэтому визуальные параметры не исчезают вместе с сезоном. «Убрать из
магазина» = `active = false`, а не удаление строки. Единственный остававшийся риск —
физическое удаление каталожной строки (у `student_items.item_code` нет FK: таблица
старше магазина) — закрыт триггером `shop_items_protect_owned`: удалить предмет,
которым кто-то владеет / который надет / стоит на витрине, теперь нельзя.

Backfill покупок не потребовался: данные уже лежат в правильном месте.
`render_payload` пуст у титулов и короны **по устройству каталога** (миграции 008/010) —
их превью строится по слоту, и выдумывать payload не нужно. Диагностический запрос
«пустой payload там, где он действительно нужен (frame/background/name_color)» — в
`database/tests/b2_stabilize_inventory.sql`.

### 4.3. Безопасность

- Владение проверяет сервер (`equip_item`, `set_showcase`), а не клиентский JavaScript:
  надеть чужой или некупленный предмет подменой запроса нельзя.
- Возможность экипировки не привязана к запросу списка текущего магазина.
- Клиенту не выдано прав менять итоговый рейтинг, создавать сезоны или назначать себе
  владение: записи в `students`, `seasons`, `student_items`, `student_equipment`,
  `season_results`, `league_*` отозваны у `anon`/`authenticated` (миграции 042/043), всё
  идёт через `SECURITY DEFINER` gateway'и с проверкой роли.
